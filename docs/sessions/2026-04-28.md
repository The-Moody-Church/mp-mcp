# 2026-04-28 — Aggregation Tools, Tool Logging, and Two Smoke-Test Fixes

## Summary

Three PRs landed today, all driven off the same loop: ship a tool, capture invocation traces in production, mine the log, fix what surfaced.

- **PR #18** — Aggregation helpers, schedule tool, attendance summaries, group drift detection, `query_table` pagination metadata, `describe_table` FK hints, and structured tool-invocation logging gated on `TOOL_LOG_PATH`.
- **PR #19** — Five fixes mined out of the first ~30 logged calls: `Metric_Title` (was wrongly `Metric_Name`), `group_by_count` returning `{id, label, count}` for FK joins, URL-length fallback threshold dropped 4096 → 2000, 23 lookup/reference tables added to the allowlist, and a curated FK catalog with `label_column` baked into `describe_table`.
- **PR #20** — Regression introduced by PR #19: when `group_by_count` added the FK ID column to `\$select` it forgot to qualify with the source table, so MP returned "Ambiguous column name" any time the FK ID column collided with the lookup's PK (which is always — `Participant_Engagement_ID` is the PK of `Participant_Engagement`, etc.).

## PR #18 — aggregation tools + tool logging

Six commits' worth of tool-surface work.

### New tools

| Tool | What it collapses |
|------|-------------------|
| `count_rows(table, filter?)` | Server-paginated count, capped at 50k |
| `group_by_count(table, group_by, filter?)` | Bucketed count without sending raw rows back to the model |
| `birth_date_range_for_age(min_age?, max_age?, as_of?, column?)` | Age-range queries that no longer depend on MP's `Age` calculated column |
| `get_schedule(date, end_date?, include_unassigned?)` | Events + Event_Rooms join, accepts `today` / `tomorrow` / `this_sunday` / `this_week` |
| `get_attendance_summary(event_name, start_date, end_date?, group_by?)` | YoY / month / week aggregation of `Event_Metrics`, pivoted by metric |
| `get_group_attendance_summary(group_id\|group_name, start_date, end_date, compare_*, ...)` | Per-participant attendance across one or two windows for pastoral-care drift |

### Existing tool changes

- `query_table` responses now carry `{ data, row_count, has_more, next_skip }` so pagination is explicit instead of "exactly 1000 means probably more". Backward-incompatible response shape, but only the model consumes the tool directly.
- `describe_table` adds `fk_join_prefix` for non-PK `_ID` columns, plus a best-guess `lookup_table` when an allowlisted plural matches.
- `get_event_attendance` pivots `Event_Metrics` to `metrics: { "In Person": 1027, "Online": 1241 }` instead of a row array, with anything missing the metric name falling through to `metrics_unnamed`.

### Tool-invocation logging

`src/utils/tool-logger.ts` patches `McpServer.registerTool` once at startup, so individual tool files don't need to opt in. When `TOOL_LOG_PATH` is set, every call appends a JSONL row `{ ts, user_id, user_name, tool, args, duration_ms, ok, error? }`. Off by default, never blocks responses, write failures only hit the console. Args are unredacted — documented in `docs/security-posture.md` with the assumption the path stays on a host-local volume.

`docker-compose.example.yml` gained a `./data:/app/data` mount paired with `TOOL_LOG_PATH=/app/data/tool-invocations.jsonl` in `.env.example`.

## TMC1 wiring for the log

The example compose and env both shipped, but the production `/srv/mp-mcp/docker-compose.yml` and `.env` were untouched. To enable in prod:

1. Added the `./data:/app/data` volume mount to `/srv/mp-mcp/docker-compose.yml`.

4. `docker compose down && docker compose up -d` to pick up the env + volume.

## PR #19 — five fixes from the first batch of logged calls

After ~30 invocations across PR #18 tool surface, the JSONL surfaced enough signal to act on.

### `Metric_Title` (was `Metric_Name`)

`get_event_attendance` and `get_attendance_summary` were selecting `Metric_ID_Table.Metric_Name` and pivoting on `row.Metric_Name`. The actual column on `Metrics` is `Metric_Title` — the join silently resolved to nothing, every metric came back with `name === ""`, and the "Sunday Morning Service" YoY query I was using as the smoke test reproduced it cleanly: `MP API GET /tables/Event_Metrics failed (500): {"Message":"Invalid column name 'Metric_Name'."}`.

### `group_by_count` returns `{id, label, count}` for FK joins

When `group_by` matches `<col>_ID_Table.<label>`, the tool now also selects `<col>_ID` and buckets by the underlying ID. Output rows are `{id, label, count}` instead of `{value, count}`. Closes a class of silent failure where MP resolves the FK label join to the wrong source table — labels can collide silently, IDs can't. The model can also cross-check the ID against the label to confirm the bucket is what it expected.

### URL-length fallback threshold 4096 → 2000

IIS rejects long requests with a generic 404 HTML page, not MP's normal JSON error. Two limits matter: URL cap (~4096) and query-string cap (~2048). The 4096 threshold only protected the URL cap, so `/tables/Event_Metrics?$filter=Event_ID IN (300+ ids)` slipped through and 404'd at IIS. Confirmed in the log:

```
{"ok":false,"args":{"event_name":"Sunday Morning Service","start_date":"2015-01-01",...},
 "error":"MP API GET /tables/Event_Metrics failed (404): <!DOCTYPE html ..."}
```

Lowered to 2000 to stay under both defaults. Happy-path queries are well below either limit; only big IN clauses change behaviour (now route to POST fallback).

### Allowlist: 23 lookup / reference tables

`describe_table("Participant_Engagement")` was rejected because the lookup table wasn't allowlisted, forcing the model to reverse-engineer the ID → label mapping by querying Participants five times. Added the FK targets we already join to (`Metrics`, `Genders`, `Marital_Statuses`, `Contact_Statuses`, etc.) plus a small set of demographic / categorization lookups (`Life_Stages`, `Household_Sources`, `Prefixes`, `Suffixes`, ...). Conservatively scoped: nothing donor / giving / Form_* / Care_* / Counseling_* / Pocket_Platform_* / Z_*. Households and Addresses stay out — still reachable via FK joins, just not direct read.

23 entries added to `config/table-access.example.json`; the production `/srv/mp-mcp/config/table-access.json` had to be merged separately (it's git-ignored). Done idempotently with a small Python script during the deploy.

### `describe_table` FK_CATALOG with `label_column`

The log surfaced multiple guess-and-fail patterns — the model picked `Participant_Engagement` as the label column on `Participant_Engagement` (wrong; `Engagement_Level`), `Metric_Name` on `Metrics` (wrong; `Metric_Title`), and `Primary_Contact_ID_Table.Display_Name` on Groups (wrong; column is `Primary_Contact`, not `_ID`-suffixed). All three would have been one-shot if `describe_table` returned `label_column` directly.

Curated catalog of `column_name → {lookup_table, label_column}` covering every FK we'd referenced in tool code or seen in failures, plus the non-`_ID` FK columns that the previous `_ID`-suffix heuristic skipped entirely (`Primary_Contact`, `Parent_Group`, `Care_Person`, `Descended_From`, `Offsite_Meeting_Address`). FK columns not in the catalog still get the existing pluralization inference; just no `label_column`.

## PR #20 — group_by_count FK ID ambiguity regression

PR #19 added `${fkIdCol},${group_by}` to `\$select` to enable the `{id, label, count}` shape, but unqualified. When the FK ID column also exists as the PK on the joined lookup table — which is always (`Participant_Engagement_ID` is the PK of `Participant_Engagement`, `Member_Status_ID` is the PK of `Member_Statuses`, etc.) — MP returns "Ambiguous column name". Pre-PR the tool only selected the label, so it sidestepped the issue entirely.

Fix: prefix the ID column with the source table name in `\$select` (`Participants.Participant_Engagement_ID,...`). Also tolerate either qualified or unqualified key shape on the response side as a defensive belt.

While in there: added `Born_From`, `Promote_to_Group`, and `Participant_Record` to the FK catalog — three more non-`_ID` FK columns the model surfaced during smoke testing of PR #19. `Donor_Record` and `User_Account` intentionally omitted (giving-related and dp_Users-related, respectively).
