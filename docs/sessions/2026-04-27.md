# 2026-04-27 — Stale Session 404 Fix

## Summary

User reported the MP MCP connector returning a generic "Error occurred during tool execution" with no detail. Traced it to a latent session-management bug: after any restart (or idle sweep, or transport-cap eviction), Claude's connector kept retrying with its pre-restart `mcp-session-id`, the SDK transport rejected the mismatched header with **400**, and Claude doesn't auto-reinit on 400. Fix: return **404** for unknown sessions per the MCP Streamable HTTP spec, which triggers the connector to start a new `initialize` handshake. Also added `[MCP]` and `[tool]` diagnostic logging — the bug was invisible because `transport.handleRequest` returns 400/200 with no console output. Shipped via PR #17.

## How we got there

`docker ps` showed the container up 6 days, port 3000 published, `/health` 200 from the public endpoint. Everything looked fine externally. First instinct was a stale OIDC token client-side, but the user retried and we watched the logs:

```
[HTTP] POST /mcp [Bearer]
[MCP] handleMcp called: POST /mcp
[MCP] authenticated user: <uuid>
```

…and then nothing. No `[MP API]` line, no exception, no error. Auth was working, request was reaching `handleMcp`, but the response path was completely silent. Both `query_table` (which calls MP) and `list_tables` (which is pure local config) were failing — that ruled out MP-side causes.

Hot-patched diagnostic logging (try/catch around `transport.handleRequest`, `res.on('finish')` for response status, plus `[tool]` enter/return/throw lines), `docker cp` of the new dist, restart, retry. The smoking gun appeared immediately:

```
[MCP] rpc=tools/call session=yes init=false
[MCP] creating new transport (sessionId=a7ec407d-... keyHit=true)
[MCP] response finish: status=400 rpc=tools/call
```

Every request was getting 400. Claude was sending `mcp-session-id: a7ec407d-...` from before the restart, the transports map was empty, our fallback created a fresh transport with a fresh session ID, and the SDK transport rejected the request because the incoming session ID didn't match the new transport's. Claude's connector loops on 400 instead of re-initializing.

## The fix

Per the MCP Streamable HTTP spec, an unknown session ID should be answered with **404** so the client knows to start a new session via `initialize`. `handleMcp` now returns 404 + a JSON-RPC error before the SDK gets a chance to 400:

```ts
if (!transport && sessionId && !isInitialize) {
  res.status(404).json({
    jsonrpc: "2.0",
    error: { code: -32001, message: "Session not found. Please reinitialize." },
    id: req.body?.id ?? null,
  });
  return;
}
```

Confirmed with the user: tool calls now succeed.

## Why now

The latent bug has existed since the 04-17 session-management work. That fix correctly created a fresh transport when no session matched, but the SDK's `StreamableHTTPServerTransport` still rejected the stale `mcp-session-id` header with 400. The container had been up for 6 days holding the same in-memory session ID, so it never surfaced. A diagnostic restart during this debug session exposed it instantly — the very act of trying to fix the (perceived) outage triggered the actual bug.

## Diagnostic logging kept

Adds ~3 lines per `/mcp` request — same level of overhead as the existing `[HTTP] / [MCP] handleMcp / [MCP] authenticated user` lines. Kept because:

- `[MCP] response finish: status=<code>` is the line that actually exposed the 400 loop. Without it, every request looked normal up to `authenticated user` and then went silent.
- `[MCP] rpc=<method> session=<yes|no> init=<bool>` makes it possible to correlate a session lifecycle (initialize → tools/call → close) without parsing request bodies.
- `[MCP] transport.handleRequest threw` catches silent SDK throws — same defensive shape as the `[MP API]` and `[verifyAccessToken]` error logs that already exist.
- `[tool] <name> called/returning/threw` covers the case where a tool handler throws and the SDK catches it into a JSON-RPC error response (which would otherwise be invisible server-side).

Precedent: the 04-17 session log notes "Response body logging kept for now — useful for debugging FK join issues" for similar reasons. Trim later if it ever shows up as noise.

## Deployment note

The fix was hot-patched into the running TMC1 container via `docker cp dist/` + `docker restart` to confirm before opening the PR. The hot-patch is wiped on the next CI image pull, so PR #17 needs to merge for the fix to persist across deploys.
